Paying down cognitive debt while you build

CIS 591 class share, Module 1. How I let Claude Code build fast without falling behind on what it built.

The idea in one line: keep building in Claude Code, do your learning somewhere else, and at the end ask for one guide written about your own repo that you can keep and come back to.

1. The problem: cognitive debt

When Claude Code works, it moves faster than we can follow. It says "next/image", "commit", "remote", "CI", and the code runs whether or not we understood any of it. Each term we skip is a small loan against our understanding. That loan is cognitive debt: the gap between what the project does and what we can explain about it.

Like any debt, a little is fine and lets you move fast. Left alone, it compounds. The day the professor asks "how does this work?", the whole bill comes due at once.

2. Two habits that keep the debt small

Habit 1: give the teacher its own lane

Everything you type in a build session becomes part of its working memory (its "context"). Long learning questions crowd out the task and can make the build worse.

My answer is a tutor built into my system: a short command for quick terms, and a separate teaching agent for deep lessons, so the build never loses its place.

No system yet? The professor's option works too: ask learning questions in the Chat tab.

Habit 2: make the decision consciously

Ask yourself: do I need this now, or later?

  • Now: it blocks my next step, or my team is waiting. Ask in Chat, then return.
  • Later: write the term down and keep building.

3. My system: a tutor on call inside Claude Code

I never leave Claude Code to learn. I built the tutor into my setup as a skill, a saved instruction set Claude loads on command.

  • Quick term: I type /eli5 mid-build. It answers in the voice of a patient mentor I modeled on Marcus Aurelius: answer first, plain words, one analogy, then the real term. A few lines, and the build carries on.
  • Deep lesson: I hand the teaching to a separate agent (a second AI worker with its own memory). It reads my repo and writes me a guide while my build session stays clean. That is how my master guide was made.

You do not need my system to start. This prompt does the same job as the skill. Paste it into your session, or save it as your own skill later.

Be my tutor, in the spirit of Marcus Aurelius: calm, patient, plain-spoken, one idea at a time. I am learning software engineering and I am not a developer.
Whenever I paste a term, an error, or a message from my coding agent:
1. Answer in one plain sentence first.
2. Explain it like I am five.
3. Then give the proper technical term and a one-line definition I could say in class.
4. Give one real-world analogy.
5. Tell me why it matters for the project I am building, and whether I need it now or can learn it later.
Stay under 150 words unless I ask for more.

To make it a skill: ask Claude Code to "save this prompt as a skill called eli5". Then /eli5 works in every session.

4. The "explain my build" prompt (once, after the build works)

This is the deep-lesson half of my system. Run it after your tests pass. In my setup a separate teaching agent runs it; without one, open a fresh Claude Code session on your project folder. Either way it can read the whole repo, and your build session stays clean.

Read this repository, its git history, and specs/module-1 (spec, instructions, rubric).
Do not change any code. Write me ONE self-contained HTML study guide, saved outside this repo, so I can explain this project in my own words.

Write it in first person, as if I am explaining it. Use the proper technical terms, and define each one in plain English the first time it appears.

Sections:
1. What the assignment asked for, and what I built
2. How the pieces connect: my laptop, Git, GitHub, Vercel, the browser (draw a simple diagram)
3. The build step by step, using my real commit history
4. Key concepts: repository, branch, commit, push and pull, local vs remote, pull request, merge, frontend vs backend. For each, give an engineer's version and a plain version with an analogy
5. Why it was built this way (spec, catalog data, tests, no backend)
6. Proof: real test results and my live links. Do not invent any result.
7. A 30-second and a 2-minute way to explain it to my professor
8. Five quiz questions with hidden answers

Be honest about what I decided and what the AI did.

Tip: Module 1's tests run with npm run check. Run them yourself first, so the guide has real numbers to cite.

5. What it produced for me

Part of the guideWhat it did for me
System diagramI can finally draw laptop to GitHub to Vercel from memory.
Concept cardsCommit, push, remote and merge each come with a plain version and an analogy.
Build timelineSeven commits, one per section, so I can walk through exactly what changed.
Professor answersA 30-second answer I can say without notes.
QuizFive questions that show me what I actually still do not know.

The biggest surprise: it caught things I would have missed. For example, the starter's product documents disagree on privacy on purpose, and the spec says to follow the 2026 policy. The guide explained why that trap exists.

6. Keep it: save it as an artifact

  • It is a single HTML file. Double-click it and it opens in any browser, no internet needed.
  • Keep it in a learning-notes folder next to your repo, not inside it, so it never gets deployed or graded by accident.
  • One guide per module. By the end of the term you have your own textbook, written about code you built.

7. The routine, start to finish

  1. Build in Claude Code: read the spec, plan, build, verify.
  2. Ask the tutor (/eli5 or the prompt) the moment a term blocks you. Park the rest in a note.
  3. Ship when npm run check passes and the site is live.
  4. Explain: run the "explain my build" prompt in a fresh session.
  5. Test yourself: take the quiz, and re-ask Chat about anything you miss.
